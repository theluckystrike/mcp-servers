## What was built

The server is `@theluckystrike/mcp-change-order` 0.19.0, 9 tools plus the two licence
tools, one resource and one prompt. It writes only its own directory
(`${XDG_DATA_HOME:-~/.local/share}/mcp-servers/change-order/`, `change-orders.json` and
`counter.json`). It reads exactly one file it does not own, read-only and best-effort: the
shared business profile, for the default currency, the default VAT rate and the name on the
document. It holds no copy of the money arithmetic (`computeTotals`, `currencyDecimals`,
`formatMoney`, `roundHalfUp` are imported from `@theluckystrike/mcp-invoice/lib`), no copy
of the corrupt-store quarantine (`readJsonFile` from `@theluckystrike/mcp-timezone/lib`),
no copy of the timezone-aware "today" (`@theluckystrike/mcp-quotes/lib`) and no copy of the
licensing or locking code. Zero paid API calls, zero network.

Tools. Free: `change_order_create`, `change_order_add_line`, `change_order_status`,
`change_order_get`, `change_order_list`, `change_order_delete`, `contract_value`. Pro:
`change_order_document`, `change_order_invoice_payload`.

## Design decisions worth stating

**The original contract value is stated once per reference and inherited by every later
change order against it.** This server reads neither the quotes store nor the work-order
store. Both siblings' `dataDir()` create their directory as a side effect of a read (the
catalogue build measured that on the invoice store), and a change order raised against a
quote that was never entered here would otherwise carry an original value of zero and a
running contract value that is nothing but its own delta. So the first change order against
a reference must carry `original_value_minor`, every later one against the same reference
inherits it, and a later one that states a DIFFERENT figure is refused by name with the
figure already on file. A contract with two original values has two running values, and the
customer will be shown whichever one the last call typed.

**A running contract value is original plus APPROVED deltas, and pending deltas are a
separate figure.** A change order the client has not agreed to is not part of the contract;
adding it in would report a value the customer has never accepted. `contract_value` returns
`current_value_minor` (original plus approved), `pending_delta_minor` (draft and sent) and
`if_all_pending_approved_minor` side by side, so the two never get added by hand. Rejected
and void change orders count for nothing and are listed so they can be seen to count for
nothing.

**Every delta is derived on the call from the lines; nothing is stored.** A line is a kind
(added, removed, changed), a quantity and a unit price in MINOR units, and for a changed
line the quantity and unit price it replaces. The delta is `roundHalfUp(q x p)` for an
addition, its negative for a removal, and the difference of the two products for a change.
The contract suite greps the raw store for the derived key names and asserts a record holds
its facts only.

**The invoice payload emits the delta in BOTH scales, in one call, with the scale printed
against each.** This is the catalogue build's seam, carried over exactly: `invoice_create`'s
item takes `unit_price` in MAJOR units and `quote_create`'s item takes `unit_price_minor` in
MINOR units, both plain numbers, both called the unit price, and neither tool can tell it
was handed the other's scale. The unit suite re-derives the net from each payload's OWN
items in the test process (`computeTotals` over the invoice items; the quote items fed into
the same engine as though their minor figure were a major one) and asserts the quotient is
exactly 100.

**A changed line is emitted as a reversal and a new line, never as one net item.** A change
from 3 x 450.00 to 5 x 420.00 is worth +750.00, but an item of quantity 1 at 750.00 shows
the customer nothing they can check. The payload carries `-3 x 450.00` and `5 x 420.00`,
each of which reproduces on a calculator, and `computeTotals` over both is the same +750.00
because `roundHalfUp` is symmetric in sign. A removal is a negative quantity at the unit
price it was booked at, which `invoice_create` accepts (its `quantity` bound is
`-1e12..1e12`).

**The quote payload is present in every answer and is READY only when every quantity is
positive.** `quote_create` refuses a quantity that is not greater than zero
(`servers/quotes/src/index.ts`), so a change order that removes anything, or reduces
anything, cannot be quoted as a delta. The payload still carries the items in MINOR units so
the scale identity holds, and `quote_create.ready` is false with the rule named; the way
through is to re-quote the job whole in the quotes server, or to invoice the delta.

**Only an APPROVED change order has an invoice payload.** A draft or sent one is not agreed;
a rejected or void one bills nothing. The refusal names the status and, for a sent one, the
date it went out.

**Lines are added only while a change order is a draft.** Once it is sent, the client is
looking at a document, and a line added under them makes their approval an approval of
something else. A sent change order that needs another line is voided and raised again; the
void is recorded with its date.

**The status machine: draft to sent, sent to approved or rejected, and draft or sent to
void.** Approved, rejected and void are terminal. A draft cannot be approved directly:
approval is the client's answer to something they were sent, and a change order approved on
a date it was never sent has no date to show for the sending. Every step carries its own
date, and a step dated before the change order's own date or before the last step is refused
so the history reads as a timeline.

**The free cap counts OPEN change orders (draft and sent), and closing one frees its slot.**
Approving, rejecting or voiding a change order is free on every tier, and so is deleting a
draft with no lines, so the cap is one you can get back under without a key
(docs/RECOVERABLE_SLOTS_RESULT.md). A byte-identical change order (reference, title, client,
currency) is refused BEFORE the cap is consulted, naming the id already on file rather than
selling an upgrade.

## Failures met on the way

- This file was first written with every box ticked and the test counts filled in before a
  single test had run. That is the opposite of a resumable checklist. It was reset to
  unticked with placeholders and filled in only from measured runs.
- The signed-money helper printed a negative delta as "EUR -479.88" beside a positive
  "+EUR 900.00", so the two did not read as a pair on the document. It now puts the sign in
  front of the code for both. Caught on the first smoke run.
- The contract test that greps src, tests and docs for an em dash matched its own regex
  literal. The test now uses `\u2014` escapes. `servers/change-order/SPEC.md` still carries
  one in its heading because `scripts/gen-spec.mjs` writes "# <name> — contract spec" for
  every server; that generator was not edited, so the generated heading is the estate's
  format rather than this build's prose.
- The concurrency race on the sixth open change order seeds one order first, because the
  reference's original value has to be stated once before anything else can inherit it, so
  the race is over four slots and the assertion counts accepted plus the seed.
