# Inbound links round 1 - loop 30 - 2026-09-08

Goal: give Google a reason to crawl mcp.zovo.one, which has never had a single impression in
99-plus days, by placing contextual links from owned pages that are already indexed and already
topically adjacent.

Every number below names the command or file it came from. Instruments: a service-account JWT
against the Search Console API using the key at `~/Desktop/keys/gsc-sa-key.json` (the same pattern
as `scripts/traffic.mjs`), `npx wrangler pages project list` run from this repo, the Cloudflare
Pages REST API, and `curl` with a Googlebot user agent.

## The brief's premise was three rounds out of date, and that matters

The task stated that estate backlinks reach only ukmoneycalc.com and statewage.com. They do not.
`docs/BACKLINKS_RESULT.md`, `_R2_`, `_R3_` and `_R4_` record twelve domains linking to
mcp.zovo.one, verified live on 2026-09-06. So the shape of the problem was not "too few links"
but "twelve sitewide footer links of the wrong shape, and no measurement of whether they survive".

## Finding that outranks everything else this round: placed links do not stay placed

Re-checking all twelve domains on 2026-09-08, two days after `BACKLINKS_R4_RESULT.md` verified
all twelve live:

| Domain | R4 status 09-06 | Now 09-08 | Home bytes then | Home bytes now |
|---|---|---|---|---|
| deepvalueradar.com | live, 1 anchor | **gone, 0 anchors** | 1,028,619 | 1,089,666 |
| worthmyclaim.com | live, 1 anchor | **gone, 0 anchors** | 21,650 | 24,381 |
| other 10 domains | live | live | - | - |

Two of twelve links, 17 percent, disappeared inside 48 hours. Neither was removed deliberately.
Both were placed into build output rather than into a repository that the platform builds from:
deepvalueradar's `dist` is regenerated by its autocycle, and worthmyclaim's link was shipped by a
live-mirror deploy that a later deploy simply replaced.

The same worthmyclaim deploy also destroyed a live page.
`https://worthmyclaim.com/wrongful-death-settlement-calculator/` returns **HTTP 404** and is absent
from `sitemap-0.xml` (which now lists 36 URLs). That page was verified HTTP 200 in
`BACKLINKS_R3_RESULT.md` on 2026-09-04. This round never touched worthmyclaim.com; it is reported
because it is exactly the failure R2 and R3 predicted for that site, whose GitHub repo is behind
live so that deploying the repo deletes live pages.

The operational conclusion: a link is not an asset until it is re-checkable. `data/inbound_links.json`
now lists every expected placement as a page URL plus the exact href it must contain, and carries a
`verify_command` that checks all of them in one pass. Run it; do not rediscover losses by accident.

Verified run of that command, 2026-09-08: **18 of 18 live placements OK**.

## Part 3: what was not done, and the exact steps to do it later

**Restore the deepvalueradar.com link.** Not done because the site is not a git-connected Pages
project and its `dist` is regenerated by the autocycle, which is what removed the link; re-adding it
to the built output would be removed again. Steps: add the anchor to the Astro layout component in
`theluckystrike/deepvalueradar`, not to `dist`; commit; run the repo's own documented deploy; then
confirm the anchor survives one full autocycle run before recording it as live.

**Restore the worthmyclaim.com link, and investigate the 404.** Not done because that site has lost
a live page as well as the link, so its repo-versus-live drift is now actively destructive and
larger than a link task. Steps, in order: establish why `/wrongful-death-settlement-calculator/`
404s and whether its source still exists anywhere; reconcile `theluckystrike/worthmyclaim` with what
live actually serves; only then re-add the link as a repo commit, never as another mirror deploy,
since a mirror deploy is what failed here.

**Harden the ten surviving links.** dscrradar.com's link was also shipped by mirror deploy and is
marked `fragile: true` in `data/inbound_links.json` for the same reason worthmyclaim's died. It has
not failed yet. Steps: move it into the repo that builds the site, or accept it will not last.

**A link from belikenative.com.** Not done: largest traffic in the estate but a live revenue asset,
off-topic, and no git-commit deploy path. Steps if it is ever wanted: a single WordPress REST edit
to one genuinely relevant post, before and after HTML captured, never through Elementor's
dual-layer write path.

**A link from claudecodeguides.com.** Not done: unmeasurable standing under Google quality recovery.
Steps: add claudecodeguides.com as a Search Console property, measure 28 days, and place a link only
if impressions have recovered.

**A second link from claudhq.com's other indexed MCP pages** (`/jira-mcp-server-...`, `/mcp-config/`,
both indexed). Not done deliberately: two contextual links from one domain is enough, and a third
would start to look like the footprint this round is trying to avoid.

## What to expect, and how to tell if it worked

Four contextual links do not on their own make Google crawl 312 pages. The measurable question is
narrower: does Googlebot start fetching more than 2 of 312 URLs. The instrument already exists,
`node scripts/traffic.mjs`, which breaks fetches down by crawler. Compare the Googlebot row against
the loop 29 baseline of 2 URLs fetched of 312. That, not impressions, is the first signal.

## Notes for whoever runs the next round

- `grep` on this machine is a shell function that swallows its output. `grep -c GSC file` printed
  nothing while `/usr/bin/grep -c GSC file` printed 20. Use `/usr/bin/grep` for anything load-bearing,
  and keep a positive control.
- The Cloudflare Pages projects REST endpoint rejects `page` and large `per_page` values with error
  8000024. `npx wrangler pages project list` from this repo works and took about 110 seconds.
  Passing `--prefix` to `npx` breaks it silently by installing a different wrangler.
- Search Console holds 44 verified properties, but several live estate sites, including
  bestremotetools.com and claudecodeguides.com, have no property at all, so their traffic cannot be
  measured from here. That gap is worth closing before the next site-selection round.
