Scorecard: **3.00 / 3** (18 of 18). Every number on every reply reproduces from
`credit-notes.json` / `purchase-orders.json` / `invoices.json` to the cent. Prompt 3 is the
interesting branch: the model neither refused outright nor silently overwrote the invoice total,
it credited exactly the remaining creditable amount and said so, which is the documented
design decision in docs/BILLING_DOCS_RESULT.md ("A credit note can never exceed the invoice's
remaining creditable amount").

### Not defects

- Prompt 5 recorded a note ("1 of 2 servers arrived") rather than a structured received-quantity
  field. `purchase_order_receive` has no such field by design (see the gap-fill row below); the
  full/partial status machine is the guard against over-receiving, and the model used it correctly.
- `billing_docs_report` being Pro-gated on the free tier for prompt 6. Documented free/Pro split;
  the model worked around it correctly with two free list calls rather than buying a licence or
  fabricating a number.

## Part 1 - probes not yet covered in docs/BILLING_DOCS_RESULT.md

RESULT.md's 20-row table already covers over-credit by amount and by line quantity (rows 1, 4),
double-credit and partial-credit-to-exact (rows 2-3), multi-currency purchase order lines (row
11), ambiguous references (row 12), corrupt stores (row 13), two-process id allocation and the
credit-cap race (rows 14-15), and free vs Pro (row 16). The rows below are the ones that table
does not carry.

| # | Probe | Result | What happens |
| --- | --- | --- | --- |
| I | credit by lines with a quantity above the invoice line | PASS (already asserted in `test/adversarial.test.mjs`) | `line 1 ... was invoiced with a quantity of 10, so 11 cannot be credited. Nothing was stored` |
| J | credit on a paid invoice | PASS | crediting does not check invoice `status`; a paid invoice can be credited (a refund after payment is normal), and the credit note is stored correctly against it. Not a defect: payment and crediting are separate facts and the design note in RESULT.md already says the invoice is never written to |
| K | a credit in a different currency | PASS by construction | `credit_note_create` has no `currency` parameter at all (asserted against the tool's own `inputSchema` in the new test): every credit note takes the invoice's stored currency, so "a credit in a different currency" cannot be expressed as an input in the first place |
| L | a 0-amount credit | PASS | `amount_minor` is `z.number().positive()`; `0` is refused at the schema, before any server code runs. Nothing is written to `credit-notes.json` |
| M | a purchase order with a negative quantity | PASS | `quantity` is `amount("quantity").gt(0, ...)`; `-5` is refused at the schema. Nothing is written to `purchase-orders.json` |
| N | receive more than ordered | PASS by construction, not by quantity check | `purchase_order_receive` carries no quantity field at all, only `partial: boolean` and a free-text `note`; there is no number to be "more than ordered". The actual guard is the status machine: a second `partial: false` receive after the order is already `"received"` is refused by name ("already received in full on ..."), which is what stops the order from being recorded as delivered twice regardless of what the note text claims |
| O | a corrupt store | PASS (already asserted in `test/corrupt.test.mjs`, rows 13 of RESULT.md) | re-verified during this pass, unchanged |
| P | two processes racing the monthly free-tier cap | PASS | new test: two client processes, one shared data dir, 8 concurrent `purchase_order_create` calls with no licence key. Exactly 5 land, exactly 3 are refused by name, and `purchase-orders.json` never holds more than 5. `purchase_order_create` and `credit_note_create` share the same `billing-docs` lock file (`locked` / `lockedWithInvoice` both call `withFileLock(lockPath(), ...)` first), so the check-then-write on `docsInMonth` is one critical section across both tools and both processes, the same mechanism that already made the credit-cap race (RESULT.md row 15) safe |

### No defects found in this pass

All 6 new probes (J, K, L, M, N, P; I and O were re-verifications of existing coverage) passed on
the shipped build. The design choices that make this so, found while reading `src/index.ts` and
`src/store.ts`:

- `credit_note_create` simply has no `currency` field to misuse.
- `amount_minor` and `quantity` are both range-checked in the zod schema (`positive()` / `gt(0)`),
  so a zero or negative value never reaches the handler.
- `purchase_order_receive` tracks a status enum (`open` / `partially_received` / `received`) and a
  receipt log, not per-line received quantities, so "received more than ordered" has no
  representation to exploit; the status guard against re-receiving a completed order does the
  actual protective work.
- The monthly-cap check and the store write are inside the same `withFileLock` critical section
  used for the credit-note-over-invoice race, so the fix already shipped for that race also covers
  this one.

Six new tests were added to `servers/billing-docs/test/gapfill.test.mjs` to keep this pass from
regressing silently: paid-invoice crediting, the absent currency parameter, zero-amount refusal,
negative-quantity refusal, receive-twice-in-full refusal, and the two-process cap race.
