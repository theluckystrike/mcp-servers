1. How it works

Each product is an MCP (Model Context Protocol) server: a small Node program that an AI client such as Claude Desktop, Claude Code or Cursor starts on the user's machine and talks to over stdin/stdout. The client asks the server which tools it has, and the model calls those tools during a conversation. Nothing runs on your infrastructure; the user's own laptop runs the server.

1 InstallTwo paths. Local: one line in the MCP client config, npx -y @theluckystrike/mcp-time-tracker. Zero-install: open https://mcp.zovo.one/mcp/connect, copy the ready URL for any of the 19 hosted servers straight into Claude.ai, Claude Desktop, Claude Code, Cursor or VS Code, no header field needed.
2 HandshakeClient sends initialize, then tools/list. Server answers with 10-14 tools plus license_status and license_activate (hosted servers add whoami).
3 UseUser says "start a timer for Acme". Model calls timer_start. Data is written to a local JSON file, or to that user's tenant document on the hosted worker.
4 Hit a limitFree tier caps something (7-day reports, 3 price watches, 200-row writes, 3 invoices a month). The tool returns the upgrade text with a checkout link tagged to the exact tool that produced it, instead of an error.
5 BuyUser opens mcp.zovo.one/buy/<product>, pays $19 (or $39 for the 19-server bundle, a $322 saving) through Stripe Checkout, sees a license key on the success page.
6 ActivateUser says "activate license MCPL1...". Server verifies the Ed25519 signature offline, saves the key, unlocks Pro. No phone-home, ever. On a hosted anonymous connection the same purchase binds to that connection automatically, nothing to paste.

Invoice was added because it closes the loop with time tracking: hours become an invoice PDF in the same chat. 3. How payment is processed

user in chat  --upgrade text-->  https://mcp.zovo.one/buy/time-tracker
Worker GET /buy/:product  --Stripe REST-->  Checkout Session (mode=payment, price_xxx)  --303-->  checkout.stripe.com
user pays (card, Link, Apple Pay; Stripe handles VAT collection if enabled on the account)
Stripe --webhook checkout.session.completed--> Worker POST /webhook  -> mint key, store in KV
Stripe --redirect--> Worker GET /success?session_id=cs_xxx -> verify payment_status=paid -> show the SAME key from KV
key = "MCPL1." + base64url({v:1, p:"time-tracker"|"*", id, iat, h:sha256(email)[0:12]}) + "." + base64url(ed25519_sig)
server: license_activate(key) -> verify with embedded public key -> save -> Pro
  • Why Checkout Sessions and not Payment Links. Measured across this estate: Stripe Payment Links converted 0 of 74 sessions in 30 days; backend-created Checkout Sessions converted 21.3%. So the worker creates the session server-side.
  • Why one-time, not subscription. Subscriptions need dunning, a customer portal and support load. A $19 lifetime key needs none of it, and offline Ed25519 keys cannot be revoked anyway. Expiry is supported in the key format (exp field) if a yearly tier is wanted later.
  • Fees. Stripe standard pricing, roughly 2.9% + $0.30 for cards in the US and 1.5% + EUR 0.25 for EU cards, taken before payout. No marketplace cut: the MCP registries have no billing rail, which is exactly why this stack exists.
  • Tax. Digital goods sold from Poland. Under the EU cross-border SME scheme you are exempt in other member states below EUR 100k; enable Stripe Tax if US sales approach the 200-transaction nexus threshold in a state.
  • Refunds. Handled in the Stripe dashboard. The key keeps working after a refund (offline verification); acceptable at $19.
  • Agent payments (x402). Optional second rail for AI agents paying per call on a hosted endpoint. The seller wallets and PayAI facilitator stack from earlythunder.com are reusable. Not wired in this session; humans do not use x402, and the measured genuine x402 volume is small.
  • Checkout wording, audited against the live Stripe session, 2026-09-05. Every one of the 20 Stripe Products now carries a real description (e.g. bundle: "Nineteen MCP servers for Claude, one lifetime key, saves $322 against buying singly"); before this the $322 saving and the server count existed only in the storefront's own HTML and never reached the Stripe page. The session now sets custom_text.submit (a cross-sell line on single-product pages, pointing at the bundle) and custom_text.after_submit (how the key arrives, and that a hosted connection upgrades automatically), customer_creation: "always" so a support lookup has an email to search, and allow_promotion_codes: false since no discount code exists. automatic_tax stays off deliberately: EU VAT (OSS) needs a jurisdiction registration only the account owner can enter. Left unfixable from here: Stripe's own branding (Dashboard-only, still default with no logo) and the fixed "Stripe Checkout" page title with no Open Graph tags, so a shared checkout link never previews the product.
  • Click instrument: does the upgrade text actually get clicked. Every /buy/<product> link a cap message produces carries src=<product>.<tool> (73 call sites across 19 servers tag the exact tool that produced the message; storefront, guide, compare and setup-page links tag themselves as store.*). The billing worker counts each click into Cloudflare KV before redirecting to Stripe, and GET /stats/clicks reads it back with no auth needed (only a tag and a count, no personal data): a daily bucket and a lifetime total per src. This is what tells "the message was never read" apart from "the message was read and did not convert" -- both used to look like zero. Current KPI read from it: 24 upgrade-link clicks in the trailing 7 days, 0 paid sessions.

Expectation set by the research: the median MCP server has never been used (66.3% of 4,811 sampled at zero) and 9,355 servers were first published in August 2026 alone. The two things that separate a listed server from a used one are a README that shows the exact config snippet for each client, and a first-run experience that works on the first tools/call. Both are gated in this build. Measured result so far: 1983 bundle downloads (+1975 in the last 7 days), 24 upgrade-link clicks in 7 days, 0 paid sessions.

5. How to validate it works and is stable

Ship gates (every server, every release)

  1. Build clean. npm run build -w servers/<name> exits 0 under strict TypeScript.
  2. Protocol smoke test. npm test -w servers/<name> spawns dist/index.js over stdio and runs initialize, tools/list and real tool calls in a temp XDG sandbox. Both free and Pro paths run (Pro key minted by scripts/sign-license.mjs). Measured for time-tracker: 2 tests, 2 pass, 255 ms.
  3. Licence package. npm test -w packages/mcp-license: 6 tests (valid, bundle, wrong product, expired, tampered, garbage). Measured 6/6 pass.
  4. Fresh-machine install. From an empty temp dir: npx -y @theluckystrike/mcp-<name> must start and answer initialize within 5 s. Run after every npm publish; this catches missing dist files and wrong bin paths, the two most common MCP install failures.
  5. Client integration. claude mcp add <name> -- npx -y @theluckystrike/mcp-<name> then claude mcp list shows it connected; one real conversation exercises one tool per server.
  6. Billing end to end. curl -I https://mcp.zovo.one/buy/time-tracker returns 303 to checkout.stripe.com; a test-mode checkout (card 4242) lands on /success and the shown key passes /verify?key= and license_activate.
  7. Adversarial audit. A separate agent tries to break each server: bad inputs, huge files, missing files, concurrent writes, non-UTF8 CSV, price pages with no price. Findings feed back before publish.
  8. Independent model review. A separate model (Codex) reviews the billing worker and, separately, the hosted remote worker, for correctness and security issues before each is treated as done. See docs/CODEX_REVIEW.md and docs/CODEX_REVIEW_REMOTE.md.
  9. Release checker. scripts/release-check.mjs reads roughly twenty wiring lists a server has to appear in outside its own folder (both registry manifests, the office-suite proxy, build scripts, the Stripe product table, setup pages for six clients, a guide, a compare page, demo assets, container/marketplace descriptors) and fails closed on any gap, with a dated waiver table for known content gaps only. It runs first inside scripts/build-mcpb.sh, so a half-wired server cannot become a .mcpb. Current state: 0 recorded gaps, 0 waivers, across 24 checks over 19 servers.

Totals at v0.9.4: 17 rounds of user-value testing through a real MCP client to date (one prompt per conversation, scoring what the tool actually said back rather than whether the call returned), latest round R17 at 72% (13 of 18 scenarios), best-ever 100% reached by 11 of 19 servers; 20 of 144 defects found across all rounds still open; 471/471 live validation checks passing (node scripts/validate.mjs); a checkout audit against the live Stripe account (docs/CHECKOUT_AUDIT.md) and a click-through instrument on every upgrade link (docs/CONVERSION_INSTRUMENT.md), both verified against live requests, not read off source.
