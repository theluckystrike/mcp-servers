# Paid Gap Analysis — "97 human checkout sessions, 0 paid, 0 license keys" (s20261012)

STATUS: complete

## Findings

**The gap is a measurement error, not a broken funnel. Nobody has ever completed a
payment on mcp.zovo.one, and the code correctly reflects that.**

Evidence (Stripe `checkout sessions list --live --limit 100`, run 2026-10-12):

1. The Stripe account serves multiple storefronts. Of the last 100 sessions:
   - 30 success_url = `backend.belikenative.com/billing` (other business)
   - 28 success_url = `zovo.one/extension-engine/...` (other storefront)
   - 20 success_url = `mcp.zovo.one/success` (this storefront)
   - 22 misc (`stripe.com`, aiwebsitepipeline, recipetool, etc.)
2. The 13 sessions with `payment_status=paid` on the account are ALL from
   extension-engine and belikenative — **zero** are mcp.zovo.one sessions.
3. All 20 genuine mcp.zovo.one sessions: `status=expired, payment_status=unpaid`.
   None reached payment. Two were tagged `probe=1`; the rest have no src metadata.
   `balance_transactions list --live` shows 0 charges matching MCP descriptions —
   no money ever entered Stripe from this storefront.
4. `scripts/kpi.mjs` computed `human_sessions` by filtering ONLY on the probe tag,
   not on success_url. It therefore counted every untagged session on the account —
   97 — including 77 checkout sessions created by other storefronts. Meanwhile the
   `paid` KPI already filtered on `success_url` starting with `https://mcp.zovo.one/`,
   which is why paid=0 was honest. The funnel KPIs were comparing apples (account-wide
   session count) to oranges (storefront-scoped paid count).

Hypotheses from the task, dispositioned:
- H1 (webhook not configured / wrong route): NOT the cause. `billing/src/index.js`
  handles `checkout.session.completed` (POST /stripe/webhook, signature-verified,
  logs `WH checkout.completed verified`, calls fulfillAndMint, releases money-guard).
  Irrelevant anyway: there are zero completed payments to deliver.
- H2 (/success mints client-side only): NOT the cause. `/success` retrieves the
  session server-side via Stripe API, verifies `payment_status === "paid"`, then
  mints the Ed25519 key and stores it in KV. The flow never executes because no
  session was ever paid.
- H3 (stale webhook secret): NOT the cause — same reason as H1/H2.

## Root Cause

`scripts/kpi.mjs` line 64: `human_sessions` counted untagged sessions account-wide
instead of scoping to the mcp.zovo.one storefront. The 97 "human checkout sessions"
were 77 other storefronts' sessions + ~20 real mcp.zovo.one session creations, none
of which completed payment. 0 paid and 0 licenses is the CORRECT measurement of
zero purchases; only the top-of-funnel number was wrong.

Secondary observation: the 20 real mcp.zovo.one sessions cluster (2026-09-24 06:25–06:53
paired bursts of invoice+time-tracker; 2026-10-07 03:38–03:40 four products in 2
minutes) with no `src` metadata — consistent with crawler/prefetch traffic rather
than human buyers, or at best humans who opened checkout and abandoned. Either way
the true funnel problem is "sessions created but never paid", which is a conversion
problem (~20 attempts, 0 completions), not a fulfillment problem.

## Fix Applied

- `scripts/kpi.mjs`: `human_sessions` now filters on the same
  `success_url startsWith https://mcp.zovo.one/` predicate that `paid` uses, and
  `human_sessions_account_wide` is kept for cross-checking.

## Verification

- Re-ran `node scripts/kpi.mjs` → regenerated `data/kpi.json`:
  - Checkout sessions from humans (storefront) = **17** (was 97)
  - human_sessions_account_wide = 97 (kept for reference)
  - Paid sessions = 0, License keys minted = 0 (unchanged — honest)
- `node --test` in `billing/`: all tests pass.
- No changes to `billing/src/index.js`; no deploy needed (worker code is correct).

## Instrumentation vs Product

**INSTRUMENTATION.** The counter was wrong (inflated numerator, wrong scope), not the
buyer journey. Evidence that buyers get licenses when they pay: the /success handler
requires `payment_status === "paid"` from the Stripe API and then mints + stores the
license in KV; the webhook path does the same idempotently. What would prove it
end-to-end in production without a real card: a Stripe test-mode checkout against the
worker with a test webhook secret, or a live purchase — next sprint should run one
$1 live test purchase and verify license key delivery in KV + email path.

Next-sprint problem is different from the one posed: ~20 real checkout attempts with
0 completions is a checkout-conversion problem (abandonment), not a fulfillment bug.
